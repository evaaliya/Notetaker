# SPEC — Notetaker (Задание 1)

Версия: 1.0 · Статус: к реализации · Язык документа: RU

## 0. Цель и границы

Клиент-серверный notetaker: заметка = запись + событие во времени. Календарь, теги, повторы, напоминания (email + in-app), корзина, live-синхронизация между вкладками/устройствами.

**Вне объёма:** OAuth, мобильные push, вложения, шаринг заметок между пользователями, интервал повтора ≠ 1, правила вроде «каждый второй вторник».

Сквозной принцип: **время — единственный источник правды в БД (UTC `timestamptz`), состояние напоминаний — в БД, а не в памяти процесса.** Из этого следует переживание рестартов, отсутствие дублей и корректность при нескольких экземплярах.

## 1. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Backend | Python 3.12 + FastAPI + SQLAlchemy 2 (async) + Alembic | Нативные WebSocket и async для live-событий; `zoneinfo` даёт корректную работу с DST; быстрая итерация с агентом |
| Frontend | React 18 + TypeScript + Vite + TanStack Query + TanStack Virtual + FullCalendar | Query — кэш и инвалидация по WS-событиям; Virtual — списки в тысячи строк без лагов; FullCalendar закрывает month/week/day и drag-and-drop |
| БД | PostgreSQL 16 | `FOR UPDATE SKIP LOCKED` (очередь напоминаний), `LISTEN/NOTIFY` (fan-out событий), `pg_trgm` (поиск), partial-индексы |
| Почта | MailHog (SMTP-заглушка, UI на :8025) | Реальный SMTP-путь без внешнего сервиса; письма видны глазами |
| Планировщик | Собственный DB-poll воркер (не APScheduler/cron в памяти) | Задачи в памяти теряются при рестарте; строки в БД — нет |
| Авторизация | Логин + пароль (argon2), opaque-сессия в httpOnly cookie | Нужна идентичность для «двух устройств»; cookie работает и для WebSocket без доп. логики |
| Тесты | pytest + реальный Postgres (testcontainers), Playwright | Мок БД не доказывает блокировки и уникальные ограничения |

Свой генератор повторов (daily/weekly/monthly) вместо `rrule`: поддерживаем ровно три частоты, а правило «31-е → последний день месяца» в `rrule` отсутствует (он пропускает месяц).

## 2. Архитектура

```
 Browser tab A ─┐                      ┌──────────────┐
 Browser tab B ─┼─ HTTP + WebSocket ──▶│  api (FastAPI)│──┐
 Browser dev. 2 ┘                      └──────┬───────┘  │ SQL
                                              │ LISTEN    ▼
                                              │       ┌────────────┐
                              pg_notify ◀─────┴───────│ PostgreSQL │
                                                      └─────▲──────┘
                       ┌───────────────┐   claim/SKIP LOCKED│
                       │ worker        │────────────────────┘
                       │ - reminders   │──▶ MailHog (SMTP)
                       │ - outbox      │
                       │ - materializer│
                       │ - trash purge │
                       └───────────────┘
```

- `api` и `worker` — один образ, разные команды. Падение/рестарт `api` не влияет на напоминания.
- Любое изменение пишет `pg_notify('u_<user_id>', {type, ids, version})` **в той же транзакции**: событие уходит только после commit, потерянных/«призрачных» событий нет.
- Каждый `api`-процесс слушает канал и рассылает событие своим WebSocket-клиентам этого пользователя.

## 3. Модель данных

```sql
users(id uuid pk, login citext unique, password_hash text,
      email text null, timezone text not null default 'UTC', created_at timestamptz)
sessions(token_hash text pk, user_id uuid, expires_at timestamptz)

tags(id uuid pk, user_id uuid, name text, color text /* #RRGGBB */,
     unique(user_id, lower(name)))

notes(id uuid pk, user_id uuid,
      title text, body text,
      starts_at timestamptz not null,          -- первое/единственное вхождение
      status text check (status in ('active','inactive')) default 'active',
      reminder_offsets int[] not null default '{}',   -- минуты: 10, 60, 1440
      version int not null default 1,          -- оптимистичная блокировка
      deleted_at timestamptz null,             -- корзина
      created_at timestamptz, updated_at timestamptz,
      -- повторы (null = одиночная заметка)
      rec_freq text null check (rec_freq in ('daily','weekly','monthly')),
      rec_until date null,                     -- включительно, в поясе rec_tz
      rec_tz text null)                        -- IANA-пояс, ЗАМОРОЖЕН при создании серии
note_tags(note_id, tag_id, pk(note_id, tag_id))

occurrence_overrides(note_id, original_start timestamptz,
      is_deleted bool default false,
      title text null, body text null, starts_at text null,   -- null = не переопределено
      pk(note_id, original_start))

reminders(id uuid pk, note_id, occurrence_start timestamptz, offset_min int,
      fire_at timestamptz,
      status text check (status in ('pending','sent','skipped','missed')),
      unique(note_id, occurrence_start, offset_min))

notifications(id uuid pk, user_id, reminder_id uuid unique,
      title text, body text, created_at timestamptz, seen_at timestamptz null)

email_outbox(id uuid pk, reminder_id uuid unique, to_addr text, subject text, body text,
      status text check (status in ('pending','sent','failed')), attempts int default 0,
      message_id text, sent_at timestamptz null)
```

**Индексы:**
- `notes(user_id, starts_at, id) WHERE deleted_at IS NULL` — календарь, сортировка по дате заметки
- `notes(user_id, updated_at, id) WHERE deleted_at IS NULL` — сортировка по изменению
- `notes(deleted_at) WHERE deleted_at IS NOT NULL` — очистка корзины
- `GIN (lower(title || ' ' || body) gin_trgm_ops)` — поиск
- `reminders(fire_at) WHERE status='pending'` — выборка воркера по частичному индексу, размер индекса не растёт с историей
- `unique`-ограничения выше — это и есть гарантия «ровно одно»

## 4. Правила предметной области

### 4.1 Заметки
- Поля: заголовок, текст, `starts_at`, теги (M:N), статус, `reminder_offsets`.
- CRUD + `POST /notes/{id}/activate|deactivate`.
- Удаление = `deleted_at = now()`; запись остаётся, из календаря/списка исчезает. Восстановление = `deleted_at = null`.
- Автоочистка: воркер раз в час `DELETE FROM notes WHERE deleted_at < now() - interval '30 days'` (каскад на теги/overrides/reminders).

### 4.2 Теги
CRUD, цвет `#RRGGBB`, имя уникально без учёта регистра в рамках пользователя. Удаление тега снимает его с заметок (каскад на `note_tags`), заметки не затрагиваются. Переименование/смена цвета отправляет событие `tag.changed`.

### 4.3 Повторы
- Частоты: daily / weekly (тот же день недели, что у `starts_at`) / monthly (тот же день месяца).
- **Правило 31-го:** если в месяце нет нужного числа — вхождение ставится на последний день месяца (31 янв → 28/29 фев → 31 мар; якорь остаётся 31).
- Вхождения генерируются **в поясе `rec_tz` по локальному времени** (поэтому «каждый день в 09:00» остаётся 09:00 после перехода на летнее время), затем переводятся в UTC. Несуществующее локальное время (DST-gap) сдвигается вперёд на разницу смещений.
- `rec_tz` фиксируется при создании серии. **Смена пояса в настройках не двигает моменты вхождений** — только их отображение.
- Вхождения не хранятся, а вычисляются на лету для запрашиваемого диапазона (бесконечная серия не раздувает БД).
- **Правка/удаление одного вхождения** → строка в `occurrence_overrides` (ключ — оригинальный момент вхождения).
- **Правка «этого и следующих»** — разделение серии: у исходной `rec_until = день_до`, создаётся новая серия с изменениями начиная с этого дня; overrides с `original_start ≥ split` переносятся на новую серию. Прошлые вхождения остаются неизменными (в т.ч. отправленные напоминания).
- **Правка «всех»** — обновление мастер-записи; overrides сохраняются.
- Удаление вхождения — не попадает в корзину (это исключение из серии); удаление серии целиком — попадает. Зафиксировано в «Известных ограничениях».

### 4.4 Напоминания

**Материализация.** `reminders` — строки на каждую пару (вхождение × интервал). Для одиночной заметки создаются сразу; для серии — на горизонт **60 дней вперёд**, воркер продлевает горизонт раз в час и при старте. Причина: бесконечные серии нельзя развернуть целиком.

`fire_at = occurrence_effective_start − offset`. При создании строки с `fire_at <= now()` **не создаются** (нельзя «напомнить в прошлом»).

**Срабатывание** (воркер, тик каждую секунду + немедленный тик после `NOTIFY reminders_changed`):

```sql
-- одна транзакция
SELECT … FROM reminders
 WHERE status='pending' AND fire_at <= now()
 ORDER BY fire_at LIMIT 100
 FOR UPDATE SKIP LOCKED;
```
Для каждой строки в **той же транзакции**:
1. Загрузить заметку; если `deleted_at IS NOT NULL` или `status='inactive'` или вхождение удалено override'ом → `status='skipped'`, выход.
2. Если `occurrence_effective_start < now()` (вхождение уже прошло, напр. из-за простоя) → `status='missed'`, письмо **не** шлём (см. 9).
3. Иначе: `INSERT notifications` (unique по `reminder_id`), `INSERT email_outbox` (unique по `reminder_id`), `status='sent'`, `pg_notify`.
4. Commit.

`SKIP LOCKED` + `unique(reminder_id)` — два воркера физически не могут обработать одно напоминание дважды. Письмо отправляет отдельный цикл outbox (SMTP вне транзакции БД, иначе долгий SMTP держит блокировки).

**Честная гарантия доставки email:** «ровно одно» обеспечено на уровне записей (одна строка outbox на напоминание). Если процесс упадёт между успешным SMTP-ответом и пометкой `sent`, при повторе уйдёт дубль — это неустранимое свойство at-least-once SMTP. Снижение риска: фиксированный `Message-ID` на строку outbox (почтовые клиенты/серверы дедуплицируют). Описано в STATUS.md.

**Реакции на изменения (без мутации reminders там, где можно проверить при срабатывании):**

| Событие | Что происходит | Почему так |
|---|---|---|
| Деактивация | Ничего не трогаем | Воркер проверяет статус в момент срабатывания |
| Активация до срока | Ничего не трогаем | Pending-строки живы → напоминания «возвращаются» |
| Активация после срока | Просроченные уже `skipped` (воркер отметил при срабатывании) → не досылаются | Следствие шага 1 |
| Удаление | Ничего не трогаем; при срабатывании `skipped` | То же |
| Восстановление из корзины | Pending с `fire_at` в будущем срабатывают; просроченные уже `skipped` | Ровно по требованию |
| Смена времени/интервалов | В одной транзакции: удалить `pending` заметки, пересоздать по новым данным (`ON CONFLICT DO NOTHING`), `sent`-строки остаются | Новый момент → новый ключ `(note, occurrence_start, offset)` → не конфликтует с уже отправленным |
| Редактирование override вхождения | Пересчёт reminders этого вхождения | Тот же механизм |

### 4.5 Часовые пояса
- БД и API оперируют ISO-8601 с `Z`. Клиент форматирует через `Intl.DateTimeFormat(…, {timeZone: user.timezone})`.
- Смена пояса в настройках → событие `settings.changed` → все вкладки перерисовывают время. Напоминания (`fire_at` в UTC) не пересчитываются.
- Поле ввода времени в форме интерпретируется в текущем поясе пользователя и сразу конвертируется в UTC на клиенте.

## 5. Realtime

- `GET /ws` (cookie-аутентификация). Сообщения сервер→клиент:

| type | Когда | Реакция клиента |
|---|---|---|
| `note.changed` / `note.deleted` / `note.restored` | любое изменение заметки (включая другую вкладку) | инвалидация запросов: заметка, календарь, список, «Ближайшее», корзина |
| `tag.changed` | CRUD тегов | инвалидация тегов и списков |
| `settings.changed` | email/пояс | перерисовка времени |
| `notification.new` | воркер отправил напоминание | toast в момент получения |
| `notification.seen` | какая-то вкладка показала/закрыла toast | убрать этот toast в остальных вкладках |

- **Не показывать повторно:** клиент после показа toast вызывает `POST /notifications/{id}/seen` (ставит `seen_at`). При загрузке страницы запрашиваются только `seen_at IS NULL`, и они идут в колокольчик-инбокс **без** всплывающего toast (всплывают только пришедшие по WS за время сессии).
- **Переподключение WS:** после обрыва клиент инвалидирует все запросы (события за разрыв могли потеряться; пересинхронизация дешевле, чем журнал событий).
- **Конфликты (одновременная правка):**
  - `PATCH /notes/{id}` обязан содержать `version`. Запрос: `UPDATE … WHERE id=? AND version=?  SET version=version+1`. 0 строк → `409` с актуальной версией заметки в теле.
  - Если открытая заметка не «грязная» — форма молча обновляется по `note.changed`. Если пользователь успел набрать правки — баннер «Заметка изменена на другом устройстве»; при сохранении получаем 409 → диалог: **«Моя версия поверх» / «Принять серверную» / «Сравнить»**. Черновик пользователя не стирается до явного выбора.
- **Переход в «прошедшие» без перезагрузки:** экран «Ближайшее» делит заметки на «сегодня/неделя/прошедшие» на клиенте по хуку `useNow()`, который ставит `setTimeout` на ближайший `starts_at` (+ страховочный тик раз в 30 с и при возврате вкладки в фокус).

## 8. Масштаб и производительность

- Поиск и фильтры — **на сервере по всем записям**, клиент хранит только страницы.
- Keyset-пагинация по `(sort_key, id)`: стоимость страницы не растёт с глубиной (в отличие от OFFSET).
- Поиск: `pg_trgm` по подстроке — работает для русского/кыргызского/английского без языко-специфичных стеммеров.
- Список в списках серий: серия = одна строка (с бейджем «повтор»); фильтр по периоду для серии — по пересечению диапазона `[starts_at, rec_until]` (приближённо, см. ограничения).
- Целевые показатели на сиде 10 000 заметок: первая страница списка p95 < 150 мс; поиск p95 < 300 мс; календарь-месяц p95 < 200 мс; UI-прокрутка без дропов (виртуализация, ≤ 50 DOM-строк).

## 9. Рестарт и простой

- Всё состояние (заметки, теги, `reminders`, outbox) — в PostgreSQL. После рестарта воркер просто продолжает выбирать `pending ... fire_at <= now()`.
- **Политика для напоминаний, чей срок прошёл во время простоя:**
  - вхождение ещё **не наступило** → напоминание отправляется с опозданием (событие всё ещё впереди, польза сохранена); в письме/уведомлении нет специальной пометки, время вхождения указано;
  - вхождение **уже прошло** → `status='missed'`, письмо не шлётся (напоминать о прошедшем — шум); запись видна в «Ближайшее → прошедшие».
- Лимит пачки 100 строк за тик — после долгого простоя не отправляется лавина разом, а разбирается за несколько секунд.

## 10. Доказуемость

Принцип: каждое поведение из задания привязано к автоматическому тесту; `make verify` запускает всё и пишет `reports/verify-<timestamp>.md`.

**Управление временем в тестах:** весь код читает время через `Clock` (в проде — системные часы, в тестах — управляемые). Воркер имеет чистую функцию `tick(now)`, поэтому «через 10 минут» проверяется без `sleep`.

| # | Требование | Механизм | Тест |
|---|---|---|---|
| T1 | Письмо ровно одно на напоминание | `unique(reminder_id)` в outbox, `SKIP LOCKED` | `test_reminder_single_email_with_two_workers` (2 воркера, 1000 тиков) |
| T2 | In-app toast во всех вкладках одновременно | `pg_notify` → WS | `e2e_toast_in_two_tabs` (Playwright, 2 контекста) |
| T3 | Не всплывает снова после reload | `seen_at` | `e2e_toast_not_repeated_after_reload` |
| T4 | Неактивная не напоминает | проверка при срабатывании | `test_inactive_note_no_reminder` |
| T5 | Активация до срока / после срока | pending vs skipped | `test_reactivate_before_due`, `test_reactivate_after_due_no_backfill` |
| T6 | Смена времени/интервала переносит | пересоздание pending | `test_reschedule_moves_reminders`, `test_sent_not_resent_on_edit` |
| T7 | Удаление отменяет, восстановление возвращает будущие | skipped/pending | `test_delete_cancels`, `test_restore_returns_future_only` |
| T8 | Корзина чистится через 30 дней | purge-джоб | `test_trash_purge_30d` (граница 29д23ч / 30д0ч) |
| T9 | Повтор: напоминание на каждое вхождение | материализация | `test_series_reminder_each_occurrence` |
| T10 | «Начиная с этого дня» не трогает прошлое | split серии | `test_split_series_keeps_past` |

## 13. Известные ограничения (будут продублированы в STATUS.md)

- Интервал повтора только 1; нет «по дням недели» и «последняя пятница».
- Фильтр по периоду для серий приближённый (по пересечению диапазона, а не по реальным вхождениям): возможны ложные попадания серии в узкий период.
- Удаление отдельного вхождения серии не попадает в корзину.
- Email: гарантия «ровно одно» на уровне записей; при падении между SMTP и пометкой возможен дубль (см. 4.4).
- Нет пересинхронизации по журналу событий — только полная инвалидация после реконнекта.
- Горизонт материализации 60 дней: напоминание вхождения дальше горизонта создаётся ночным/часовым продлением, а не сразу.
- Без rate-limit, без сброса пароля, без подтверждения email.
