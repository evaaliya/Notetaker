**User**

1. **Потерянный ответ нельзя воспроизвести одним `setOffline`.** Он обрывает запрос до сервера. Дубли возникают, когда сервер запрос обработал, а ответ потерялся. Для этого нужен `page.route` с `route.fetch()` и последующим `route.abort()`. Без этого сценария (b) проверит не то.

2. **Граничные случаи идемпотентности create.** Сейчас в плане только «повтор с тем же id → одна заметка». Нужно решить заранее:
   - тот же id с другим телом: вернуть существующую заметку или 409;
   - id уже принадлежит чужой заметке: не перезаписывать и не раскрывать её, вернуть ошибку;
   - id совпал с удалённой заметкой: повтор create не должен её воскрешать.

3. **Порядок и хранение очереди.** В плане нет:
   - зависимостей (create → PATCH → delete для одной заметки; PATCH на ещё не созданную заметку; delete заметки, у которой create ещё в очереди);
   - защиты от двойной отправки из нескольких вкладок (Web Locks или BroadcastChannel);
   - переживания перезагрузки страницы, очередь должна лежать в IndexedDB, а не в памяти;
   - реального триггера flush: событие `online` ненадёжно, нужны повтор с backoff и таймаут запроса через `AbortController`.

4. **Таймаут и зависший запрос.** Одна из ваших гипотез: запрос зависает и завершается при возврате сети. Без клиентского таймаута это не лечится. Его стоит явно включить в правила.

5. **Решение «очередь или ошибка» по каждой мутации.** Пункт 7 оставляет выбор открытым. Лучше зафиксировать его в таблице аудита:
   - повторный DELETE и restore считать успехом;
   - share не должен создавать вторую ссылку при повторе;
   - теги должны добавляться идемпотентно;
   - вложения нужно дедуплицировать (клиентский id или хэш);
   - PATCH: last-write-wins или версия/ETag, пусть агент выберет и запишет.

6. **Не фиксировать причину заранее.** Пункты 2–7 написаны так, будто гипотезы подтверждены. Пусть в плане будет оговорка: если воспроизведение покажет другую причину, агент останавливается и докладывает до правок.

7. **Мелочи.** Проверить, что номер D-118 действительно следующий в DECISIONS.md. Баннеру нужен `role="status"`.
