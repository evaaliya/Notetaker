# Лог решений

Формат записи: время · решение · альтернативы · причина.
Время агент берёт командой `date "+%Y-%m-%d %H:%M %Z"`. Записи добавляются в конец, старые не переписываются.

## Шаблон

```
### D-NNN · YYYY-MM-DD HH:MM TZ · M<этап> · <короткое название>
**Решение:** что выбрано.
**Альтернативы:** что рассматривали.
**Причина:** почему именно так (механизм, а не «так удобнее»).
**Последствия:** что это ограничивает или усложняет.
```

## Решения этапа проектирования (до кода)

Приняты при написании `spec.md` (2026-10-22), перенесены в лог 2026-10-23 при подготовке репозитория.

### D-001 · 2026-10-23 · M0 · Планировщик — опрос БД, а не APScheduler/cron
**Решение:** отдельный воркер выбирает `pending` напоминания из PostgreSQL (`FOR UPDATE SKIP LOCKED`).
**Альтернативы:** APScheduler, Celery beat, cron.
**Причина:** задачи в памяти теряются при рестарте, строки в БД — нет. `SKIP LOCKED` + unique-ограничения не дают двум воркерам обработать одно напоминание дважды.
**Последствия:** задержка срабатывания до 1 секунды (тик) — приемлема для напоминаний за 10 минут и больше.

### D-002 · 2026-10-23 · M0 · Стек: FastAPI + SQLAlchemy async + PostgreSQL 16, React + Vite + TanStack
**Решение:** Python 3.12 / FastAPI / Alembic; React 18 + TypeScript; PostgreSQL 16.
**Альтернативы:** Node.js (Fastify), Vue, MySQL.
**Причина:** нативные WebSocket и async для live-событий; `zoneinfo` корректен с DST; PostgreSQL даёт `SKIP LOCKED`, `LISTEN/NOTIFY`, `pg_trgm`, partial-индексы — на них держатся «ровно одно», live-синхронизация и поиск по тысячам заметок.
**Последствия:** привязка к PostgreSQL.

### D-003 · 2026-10-23 · M0 · Время хранится в UTC, пояс — только отображение
**Решение:** `timestamptz` в UTC; пояс пользователя применяется на клиенте.
**Альтернативы:** хранить локальное время + пояс заметки.
**Причина:** смена пояса в настройках меняет отображение, но не момент срабатывания; UTC делает это автоматическим.
**Последствия:** для серий нужен замороженный `rec_tz`, иначе «каждый день в 09:00» поедет при DST (см. D-006).

### D-004 · 2026-10-23 · M0 · Авторизация: логин + пароль, opaque-сессия в httpOnly cookie
**Решение:** argon2, сессия в БД, cookie.
**Альтернативы:** без входа, JWT, OAuth.
**Причина:** для проверки «два устройства» нужна идентичность; cookie работает и для WebSocket без отдельной логики.
**Последствия:** нет сброса пароля и подтверждения email (см. `STATUS.md`).

### D-005 · 2026-10-23 · M3 · Email через outbox с unique(reminder_id), SMTP вне транзакции
**Решение:** транзакция воркера пишет `email_outbox`; отдельный цикл отправляет; фиксированный `Message-ID`.
**Альтернативы:** отправка внутри транзакции; отправка из обработчика.
**Причина:** долгий SMTP в транзакции держал бы блокировки; unique гарантирует одну запись на напоминание.
**Последствия:** при падении между успешным SMTP и пометкой `sent` возможен дубль (at-least-once) — описано в `STATUS.md`.

### D-006 · 2026-10-23 · M5 · Собственный генератор повторов вместо `rrule`
**Решение:** свой генератор для daily / weekly / monthly.
**Альтернативы:** `python-dateutil` `rrule`.
**Причина:** нужны ровно три частоты, а правила «31-е → последний день месяца» в `rrule` нет (он пропускает месяц).
**Последствия:** генератор поддерживаем и тестируем сами, включая DST-кейсы.

### D-007 · 2026-10-23 · M3 · Политика простоя
**Решение:** напоминание, чей срок прошёл во время простоя: вхождение ещё впереди — отправляется с опозданием; уже прошло — `missed`, письмо не шлём.
**Альтернативы:** слать всё; не слать ничего.
**Причина:** напоминание о событии впереди полезно, о прошедшем — шум.
**Последствия:** лимит пачки 100 строк за тик, чтобы после простоя не уходила лавина.

## Журнал по ходу разработки

### D-008 · 2026-10-23 05:45 +06 · M0 · Alembic на sync psycopg2, не asyncpg
**Решение:** миграции гоняются через `postgresql+psycopg2://`; runtime API остаётся на `asyncpg`.
**Альтернативы:** `asyncio.run` в `env.py`; `nest_asyncio`; отдельный init-контейнер.
**Причина:** `command.upgrade` вызывается из lifespan uvicorn и из `asyncio.run` воркера — вложенный `asyncio.run` падает (`cannot be called from a running event loop`). Sync-движок для DDL это обходит без хаков.
**Последствия:** в образе нужен `psycopg2-binary` только ради миграций.

### D-009 · 2026-10-23 05:45 +06 · M0 · Heartbeat воркера — таблица `worker_heartbeat`
**Решение:** одна строка `worker_heartbeat(id=1, last_seen_at)`; `/api/health` считает воркер живым, если `last_seen_at` не старше `WORKER_HEARTBEAT_STALE_SECONDS` (10 с).
**Альтернативы:** файл на volume; отдельный Redis; проверка PID.
**Причина:** спека требует проверку воркера в `/health`; состояние должно переживать рестарт api и жить в Postgres вместе с остальным.
**Последствия:** сразу после старта api health может быть `degraded`, пока воркер не сделает первый тик.

### D-010 · 2026-10-23 05:45 +06 · M0 · `tags.name_lower` вместо functional unique index
**Решение:** колонка `name_lower` + `unique(user_id, name_lower)`.
**Альтернативы:** `unique(user_id, lower(name))` как expression index без колонки.
**Причина:** проще выразить в SQLAlchemy ORM и в тестах; семантика совпадает со спекой §3.
**Последствия:** при записи тега (M1) нужно всегда заполнять `name_lower = name.lower()`.

### D-012 · 2026-10-23 07:12 +06 · M1 · `name_lower` только через `set_tag_name`
**Решение:** единственная точка записи имени тега — `app.services.tags.set_tag_name`: `name = strip()`, `name_lower = casefold()`. Роутеры и тесты не трогают `name_lower` напрямую.
